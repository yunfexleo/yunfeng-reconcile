# 事故复盘：2.14.0 发布事故（alpha / beta / gamma）

> 日期：2026-03-12。影响：alpha、gamma 不可用约 1 小时；beta 历史数据「消失」（实际未丢失）。
> 本文回答题目两个问题：一、发生了什么、为什么；二、如果发布和值班交给我，怎么改。

---

## 一、发生了什么，为什么

表面是「发了一个坏版本」，实际是**三个相互独立的问题被同一次发布串在一起**：

| 环境 | 现象 | 直接原因 |
|---|---|---|
| alpha | 14:15 起打不开，容器反复重启 | 2.14.0 把 `MEDIA_KEY` 变为必填，alpha 的 `.env` 缺此项，启动即崩溃 |
| beta | 发布「成功」但历史数据全消失 | 在新目录 `beta-0312` 里执行 compose，project 名改变，应用连上自动新建的空白数据卷 |
| gamma | 15:06 起打不开，容器反复重启 | 14:52 只改了 db 内存上限，`compose up -d` 把 app 一并重建，从 `:latest` 拉到了坏版本 |

关键事实（证据链）：

- alpha 日志 `starting 2.14.0 → config invalid: MEDIA_KEY is required`，随后退出、每分钟重启——崩溃循环；而 beta 的 `.env` 有 `MEDIA_KEY`，所以 beta 容器本身能跑。
- beta 数据一直在原卷 `beta_pgdata`（3.1 GB 完好），应用只是连到了新卷 `beta-0312_pgdata`（61 MB 空库）。compose project 名默认取目录名，换目录 = 换一套容器名和卷名。
- gamma 当天没发布，只是日常调 db 配置，被 `latest` 浮动标签「顺手升级」。

**为什么一个小配置问题拖成 1 小时故障**——每道防线都漏了：

1. **`:latest` 可变标签**：三套环境共用浮动标签，推一次镜像三套全暴露。
2. **发布验证形同虚设**：deploy.sh 只 grep 容器名是否存在；`restart: unless-stopped` 让崩溃容器永远在列表里，检查恒为真。它验证的是「容器在」，不是「能服务」。
3. **值班误诊**：用 `grep '"level":5'` 过滤日志，漏掉致命的 `level:60 config invalid`，把常态上游 502（旧版本正常时也有 612 条/天）当成病因，浪费 25 分钟；直到 14:40 看到 `Up 3 seconds` 才发现是重启循环。
4. **告警不可见**：告警只显示在应用自己的后台里，应用崩溃后无处可看，等于没有告警；alpha 从 14:08「发布成功」到 14:15 由客户先发现。
5. **数据恢复知识缺失**：beta 的恢复只是「停掉错误 project、用正确 project 名重启」十分钟的事，值班到 16:00 还没找回数据。

## 二、如果交给我，我会怎么改

原则：让事故的每一环**不再可能发生**，或发生了**不再致命**。

### 1. 发布物：不可变标签 + 配置即契约

- 废弃 `:latest`，镜像只发不可变标签（`app:2.14.0` 或 digest），三套环境各自 pin 版本；gamma 那种日常变更绝无可能顺手升级 app。
- CI 增加配置校验：按各环境配置清单静态检查必填项，缺项直接阻断发布。应用启动时的 `config invalid` 应该是最后一道防线，而不是第一道。
- 配置变更与版本发布绑定成同一次变更，发版说明必须列出新增/废弃的配置项。

### 2. 发布验证：验证「能服务」，不是「容器在」

重写 deploy.sh 的健康检查：

- 应用提供 `/health` 且响应带版本号，发布脚本校验「健康 + 版本正确」才算成功；
- 轮询期间检查容器 `RestartCount`，出现 crash-loop 立即判失败，不等超时；
- 失败自动回滚到上一版本（旧版本保留，回滚 = 指回旧标签再 up）。

这样 alpha 会在发布 1 分钟内自动回滚并告警，而不是挂 1 小时。

### 3. 环境隔离：固定 project 名与卷名

- 启动命令显式指定 project 名，与目录解耦：`docker compose -p "$ENV" --project-directory /srv/$ENV up -d`；数据卷同样显式命名（`name: ${ENV}_pgdata`）。发布包解压到哪都不影响容器和卷的身份，beta 事故从机制上消除。
- 禁止在生产机上「试新流程」：发布路径只有一条，新流程先在测试环境验证。
- 日常变更精确操作：只动 db 就 `up -d db`，改动前 `docker compose config` diff 确认会重建哪些服务。

### 4. 告警：值班的人不看后台也要知道坏了

- 应用告警外发：崩溃、启动失败、配置校验失败直接推值班 webhook，告警通道与系统自身解耦（系统挂了也能收到）。
- 外部探针兜底：独立探针定时探测三套环境健康端点，连续失败即告警。alpha 这种「容器活着、服务死了」30 秒内报警，不用等客户反馈。
- 告警内容面向处置：带环境名、版本号、重启次数、最近一条致命日志。

### 5. 值班：减少误诊的机会

- **发布观察期制度化**：发布后 15 分钟内必须观察健康端点、重启次数、错误率与发布前基线的差异，记录结论才能离开。本次 14:08 发布、14:15 客户发现，说明发布完没人看。
- **排障先看最高级别**：fatal(60) > error(50) > warn(40)，`grep '"level":5'` 这种只匹配 50 的写法写入值班手册反面教材。
- **建立基线认知**：对上游 502 这类常态噪音做每日基线统计，排障先问「和平时比异常在哪」。
- **数据类事故 runbook**：把「compose project 名与卷名关系、连错卷的恢复步骤」写成 runbook 并演练，beta 的恢复不该拖到 16:00。

---

## 改进项与事故环节的对应

| 事故环节 | 对应改进 |
|---|---|
| alpha 坏版本通过发布检查 | 健康检查 + 自动回滚（§2） |
| 配置缺失 30 分钟无人知 | 发布前配置校验（§1）+ 外发告警（§4） |
| gamma 日常变更拉起坏版本 | 不可变标签（§1）+ 精确指定服务（§3） |
| beta 数据「消失」 | 固定 project/卷名（§3）+ runbook（§5） |
| 值班误诊（漏看 level 60、噪音当信号） | 值班手册与基线（§5） |
| 客户先于内部发现故障 | 外部探针（§4） |
