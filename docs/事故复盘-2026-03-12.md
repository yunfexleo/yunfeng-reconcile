# 事故复盘：2.14.0 发布事故（alpha / beta / gamma 三套环境）

> 日期：2026-03-12（按值班记录时间线）
> 影响范围：`alpha`、`gamma` 应用不可用约 1 小时；`beta` 历史数据「丢失」（实际未丢失，见下文）
> 复盘回答题目两个问题：一、发生了什么、为什么；二、如果三套环境的发布和值班交给我，会怎么改。

---

## 1. 结论速览（TL;DR）

这次事故表面上是「发了一个坏版本」，实际上是**三个相互独立的问题被同一次发布串在了一起**：

| 环境 | 现象 | 直接原因 | 根因类别 |
|---|---|---|---|
| alpha | 14:15 起打不开，容器反复重启 | 2.14.0 缺必填配置 `MEDIA_KEY`，启动即崩溃 | 发布物缺陷 + 发布验证缺失 |
| beta | 发布「成功」但历史数据全部消失 | 在新目录 `beta-0312` 里执行 compose，project 名改变，应用连上了**新建的空白数据卷** | 发布流程不规范 |
| gamma | 15:06 起打不开，容器反复重启 | 14:52 修改 db 内存上限后 `compose up -d`，app 被一并重建并拉到已是坏版本的 `latest` | 可变标签 + 日常变更未隔离 |

贯穿三者的系统性根因：

1. **`:latest` 可变标签**：三套环境共用同一个浮动标签，一次推镜像、三套全暴露；
2. **发布脚本的健康检查形同虚设**：只看容器名是否存在，`Restarting` 也算「deploy ok」；
3. **告警只在应用自己的后台里**，值班的人看不见，alpha 从 14:08「发布成功」到 14:40 才发现是容器在重启；
4. **值班排障时抓错了重点**：用 `grep '"level":5'` 过滤日志，漏掉了真正致命的 `level:60 config invalid`，把常态的上游 502 当成了病因。

## 2. 发生了什么：时间线还原

```
14:02  2.14.0 镜像构建完成，推送到 registry.example.com/app:latest
14:08  deploy.sh 发布 alpha → 输出 "deploy ok"
       （实际上 alpha 从未真正起来过：应用因缺 MEDIA_KEY 启动即崩溃，
         restart: unless-stopped 让它无限重启，docker ps 显示 Restarting，
         而 deploy.sh 的 grep 容器名检查照样通过）
14:15  客户反馈 alpha 打不开
14:16  值班 grep '"level":5" 日志，只看到一堆上游 502，
       判断"上游在抖，先观察" —— 误诊（见 3.2）
14:31  发布 beta。为"试新流程"把发布包解压到新目录 /srv/beta-0312/，
       在其中执行 compose up -d；端口冲突，docker stop beta-app-1 后成功
       （compose project 名默认取目录名 → 变成 beta-0312，
         于是新建了空的 beta-0312_pgdata 卷，应用连上空库）
14:33  beta 能打开，但历史数据全部"不见了"
14:40  alpha 仍打不开；docker ps 里 alpha-app-1 状态是 Up 3 seconds
       —— 这时才从"Up 3 seconds"意识到容器在反复重启
14:52  gamma：给 db 加内存上限，compose up -d。
       compose 文件变更导致 app 服务也被重建，
       重建时拉取 app:latest —— 此刻 latest 已经是缺 MEDIA_KEY 的 2.14.0，
       gamma 因此踩中了和 alpha 同一个雷（14:52:19 日志显示 starting 2.14.0）
15:06  客户反馈 gamma 打不开
15:10  docker ps：alpha-app-1 / gamma-app-1 均 Restarting (1)
15:20  把 app:latest 重新指向旧版本镜像，alpha、gamma 各 up -d 一次，恢复
16:00  beta 历史数据仍未找回（其实数据一直在 beta_pgdata 卷里，
       应用只是连错了库）
```

关键证据链：

- **alpha 日志**（14:30 一段）：`starting 2.14.0 → db connected → channels connected ok:27 failed:187 → config invalid: MEDIA_KEY is required`，随后进程退出、下一分钟重新 `starting`——崩溃-重启循环的完整一圈。
- **gamma 日志**：14:52:19 `starting version 2.14.0 → db connected` 之后无下文，与 alpha 的崩溃模式一致；gamma 唯一的发布动作是 14:52 那次 db 内存调整，说明 app 是在那次 `up -d` 中被意外重建的。
- **15:10 docker ps**：`alpha-app-1`、`gamma-app-1` 均为 `Restarting (1)`，`beta-0312-app-1` 为 `Up 39 minutes`。
- **volume 列表**：`beta_pgdata` 3.1 GB（原数据，完好）、`beta-0312_pgdata` 61 MB（新建的空库）——beta 的数据从未丢失。
- **`.env` 排查**：`/srv/beta-0312/.env` 和 `/srv/beta/.env` 都有 `MEDIA_KEY`，但 **alpha 和 gamma 的 `.env` 里没有**——这就是 2.14.0 在 alpha/gamma 崩溃、而 beta 容器本身能跑起来的原因（beta 的问题是连错库，不是起不来）。

## 3. 为什么：根因分析

### 3.1 alpha / gamma —— 坏版本 + 多重防线全部失效

直接原因：2.14.0 把 `MEDIA_KEY` 变成了必填配置，但 alpha、gamma 的 `.env` 没有这一项，应用启动时校验失败主动退出（日志 level 60 `config invalid`）。

为什么一个小配置问题演化成持续 1 小时的故障，五道防线每一道都漏了：

1. **构建/发布环节**：新必填配置没有配套的检查（CI 里没有针对各环境配置清单的校验，也没有随版本发布的配置变更说明）。
2. **deploy.sh 的验证**：`sleep 5` 后只检查 `docker ps` 里有没有 `alpha-app-1`。`restart: unless-stopped` 让崩溃的容器永远在列表里，检查恒为真。它检查的是「容器在不在」，而发布要回答的问题是「新版本能不能正常服务」——两者根本不是一回事。
3. **应用自身的告警**：只显示在应用管理后台里。应用崩溃后告警无处可看，等于没有告警。
4. **值班排障**（见 3.2）：14:16 的日志分析方向错误，浪费了 25 分钟。
5. **`:latest` 标签放大器**：gamma 当天根本没发布，只是 14:52 调了一次 db 配置，`up -d` 顺手重建 app 时就从浮动标签拉到了坏版本。如果标签不可变，gamma 这次日常变更只会动 db，不会碰 app。

### 3.2 值班误诊：一次典型的「噪音当信号」

14:16 的排查动作是：

```bash
docker logs alpha-app-1 2>&1 | grep '"level":5' | tail -40
```

两个问题：

- **过滤条件漏掉了致命日志**。崩溃原因是 `level:60`，`"level":5` 只匹配 50。致命的 `config invalid` 一条都没进视野。
- **把背景噪音当成了病因**。看到的全是上游 502，但事后对前一天（旧版本、服务正常）的日志统计，全天也有 612 条 502——这是常态噪音。没有对「什么是正常基线」的认知，异常就无从谈起。

另外，14:40 才从 `Up 3 seconds` 意识到容器在重启循环——如果 14:08 发布后做一次「等 30 秒再看容器重启次数」的检查，故障发现时间可以从 37 分钟缩短到 1 分钟。

### 3.3 beta —— compose 默认 project 名引发的「数据消失」

docker compose 的 project 名默认取当前目录名。发布包解压到 `/srv/beta-0312/` 后，project 从 `beta` 变成了 `beta-0312`：

- 容器名变为 `beta-0312-app-1` / `beta-0312-db-1`（所以原 `beta-app-1` 还占着端口，需要手动 `docker stop`）；
- **volume 名随之变为 `beta-0312_pgdata`，docker 自动创建了一个全新的空卷**；
- 应用连接串指向 `db` 主机名，在新 project 内解析到新起的空库——历史数据「全部消失」。

数据其实一直在 `beta_pgdata`（3.1 GB，完好）。恢复方法很简单：停掉 `beta-0312` 这一组，在正确位置以正确 project 名重启原 compose；beta 的事故是**纯流程事故**，与代码质量无关。事后 `grep MEDIA_KEY` 也证实 beta 的 `.env` 配置是齐的。

## 4. 如果发布和值班交给我，我会怎么改

按「让这次事故的每一环都不再可能/不再致命」的思路，分五层。

### 4.1 发布物：不可变版本 + 配置即契约

- **废弃 `:latest`**。镜像只以不可变标签发布（`app:2.14.0` 或 digest），三套环境各自 pin 住自己的版本；compose 文件里写死版本号而不是 `latest`。这样「推一个新版本」不会污染任何环境，gamma 那种日常变更也绝无可能顺手升级 app。
- **新必填配置必须在发布前被发现**。CI 增加一步：针对每个环境的配置清单（`.env` 模板 + 必填项校验）做静态检查，缺项直接阻断发布；应用启动时的 `config invalid` 是好的最后一道防线，但不应该成为第一道。
- 配置变更与版本发布**绑定成同一次变更**，发版说明里必须列「本次新增/废弃了哪些配置项」。

### 4.2 发布脚本：验证「能服务」，而不是「容器在」

重写 `deploy.sh`，核心变化：

```bash
#!/usr/bin/env bash
set -euo pipefail
ENV=$1
VERSION=$2                      # 显式传入版本，禁止 latest
cd /srv/$ENV
docker compose pull app:$VERSION
docker compose up -d app
# 健康检查：HTTP 就绪探针 + 版本号确认，而不是 grep 容器名
for i in $(seq 1 30); do
  if curl -fsS -m 2 "http://localhost:${APP_PORT}/health" | grep -q "$VERSION"; then
    echo "deploy ok: $ENV @ $VERSION"; exit 0
  fi
  # 发现崩溃重启立即失败，不等 30 次
  if [ "$(docker inspect -f '{{.RestartCount}}' ${ENV}-app-1)" -gt 2 ]; then
    echo "deploy failed: container crash-looping"; exit 1
  fi
  sleep 2
done
echo "deploy failed: health check timeout"; exit 1
```

要点：应用提供 `/health` 且响应里带版本号；检查 RestartCount 识别 crash-loop；失败即自动回滚到上一版本（旧容器保留，回滚 = 指回旧版本再 up）。

### 4.3 环境隔离：固定 project 名与数据卷名

- compose 显式指定 project 名，与环境目录解耦：

  ```yaml
  # 启动命令统一为：
  docker compose -p "$ENV" --project-directory "/srv/$ENV" up -d
  ```

  目录叫什么、发布包解压到哪，都不影响容器与卷的身份。
- volume 名也显式命名（`name: ${ENV}_pgdata`），杜绝「目录名变了就悄悄建新卷」。
- **禁止在生产机上「试新流程」**。发布路径只有一条；想验证新流程，在测试环境验证完再上线。
- db 这类有状态服务的日常调整（内存上限等）与 app 发布解耦：改动前 `docker compose config`  diff 一遍，确认会重建哪些服务；或者干脆只 `up -d db` 精确指定服务。

### 4.4 告警：让值班的人能「不看后台也知道坏了」

- 应用告警外发：崩溃、启动失败、配置校验失败，直接推送到值班 webhook（告警通道与系统自身解耦，系统挂了也能收到）。
- 外部探测兜底（ dead man's switch 思路）：一个独立于三套环境的探针定时请求各环境的健康端点；任何一套连续 N 次探测失败即告警。alpha 这类「容器活着、服务死了」的情况，30 秒内必然报警，而不是等客户 14:15 来反馈。
- 告警内容面向处置：带上环境名、版本号、容器重启次数、最近一条致命日志，值班的人不需要再登录机器现查。

### 4.5 值班：把误诊的机会变少

- **发布观察期制度化**：发布后 15 分钟内必须观察（健康端点 + 重启次数 + 错误率对比发布前基线），并记录观察结论才能离开。本次 14:08 发布、14:15 客户发现，说明发布完没人看。
- **日志分级写进值班手册**：fatal(60) > error(50) > warn(40)，排障先看最高级别，且 grep 模式要覆盖全部级别；`grep '"level":5'` 这种写法应列为反面教材。
- **建立基线认知**：对上游 502 这类常态噪音建立每日基线统计（本题材料里 612 条/天就是现成例子），排障时先问「今天和平时比，异常在哪」。
- **演练数据类事故的恢复**：beta 的恢复（连回正确的卷）是十分钟的事，但值班到 16:00 还没找回数据，说明缺少对「compose project 名与卷名关系」这一知识的准备。把它写成 runbook。

### 4.6 改进项与本次事故的对应关系

| 本次事故的一环 | 对应改进 |
|---|---|
| alpha 坏版本通过发布检查 | 4.2 健康检查 + 自动回滚 |
| 配置缺失 30 分钟无人知 | 4.1 发布前配置校验；4.4 外发告警 |
| gamma 日常变更拉起坏版本 | 4.1 不可变标签；4.3 精确指定服务 |
| beta 数据「消失」 | 4.3 固定 project/volume 名；4.6 runbook |
| 值班误诊（漏看 level 60、噪音当信号） | 4.5 值班手册与基线 |
| 客户先于内部发现故障 | 4.4 外部探针 |
